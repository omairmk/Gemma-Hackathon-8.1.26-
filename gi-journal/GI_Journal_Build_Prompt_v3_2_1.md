## 2. Architecture and invariants

- **Stack:** Gradio Blocks app (`app.py`; tabs: New Entry, Timeline, Visit Summary, Privacy & Data), Pydantic v2 (`schemas.py` from Friday), stdlib sqlite3 (WAL; connection-per-operation or locked shared connection — Gradio handlers run on worker threads), Pillow (+pillow-heif if installed Friday), httpx, pytest.
- **Model client:** exactly per PRECHECK (request template included). httpx `trust_env=False`, `follow_redirects=False`, read timeout ~120 s; temperature 0.0–0.2; max ~1024 tokens; `response_format` json_schema; parse → validate → ONE repair request → on second failure: no fabricated values, concise error, saving still offered. Never log image bytes, full model responses, or user notes.
- **Warm-up, non-blocking:** ~2 s health check at app start; only if reachable, one tiny warm-up on a background thread. Launch never waits on the model server.
- **Loopback enforcement, two layers:** (1) validator in `config.py`: model URL must be `http` with host `localhost`/`127.0.0.1`/`::1`; reject other hosts/schemes, public or private-network IPs, credentialed URLs; refuse analysis (visible indicator) otherwise. (2) Privacy self-test inspects ACTUAL endpoints — port parsed from `GEMMA_BASE_URL`, Gradio's actual bound port from the running app — via `lsof -nP -a -p <PID> -iTCP -sTCP:LISTEN` (the `-a` ANDs the criteria; without it lsof ORs them and the "proof" includes unrelated listeners). No hard-coded port list.
- **Permissions at creation time:** call `os.umask(0o077)` at process start, BEFORE initializing Gradio, SQLite, or any file writes, so the DB and its `-wal`/`-shm` sidecars, images, exports, and cache files are born 0600/0700; the self-test then verifies modes on the DB, sidecars, a sampled image, and the temp dir rather than trusting after-the-fact chmods.
- **Profile-root safety:** at startup, the active data profile is validated before ANY destructive capability is armed: canonical (realpath) resolution; refuse `/`, `$HOME`, the repo root, or any parent of the repo; on first init write an app-owned marker file (`.gi_journal_profile`); recursive deletion is permitted only inside a marker-bearing, validated profile. The "refuse non-injected directories" rule binds tests, seeders, and maintenance scripts; the in-app Delete All operates on the validated active profile precisely because it carries the marker.
- **Lifecycle lock and deletion epoch:** one app-level lock serializes upload sanitization, Clear cleanup, save, export, entry deletion, and Delete All. A global deletion epoch increments on Delete All; any pending save carrying a stale epoch (e.g., another browser tab) is rejected with a clear message. Before any write or delete, verify canonical containment inside the active profile.
- **Gradio hygiene:** `GRADIO_ANALYTICS_ENABLED=False` in the environment BEFORE importing gradio, plus `analytics_enabled=False` and `enable_monitoring=False` where the installed version accepts them. `GRADIO_TEMP_DIR = <profile>/tmp` (created under the umask); `max_file_size` 15 MB. **The entire `GRADIO_TEMP_DIR` is treated as disposable app property:** raw uploads are deleted in `finally` immediately after sanitization; the whole directory is swept at app start and on Delete All; the export registry tracks app-created copies for per-entry cleanup, but correctness never depends on the registry knowing every framework-created path — the wholesale sweep guarantees it. Integration tests assert the directory's contents after Clear, after a validation failure, and after entry deletion. **File serving:** never put the data directory in `allowed_paths`; thumbnails are returned as in-memory PIL images (Gradio caches them in our disposable temp dir); export downloads are copies placed there on request. `server_name="127.0.0.1"`, `share=False`, no debug. No remote fonts/scripts/assets; no telemetry.
- **Image sanitization:** validate via Pillow (never extension); ≤15 MB; `Image.MAX_IMAGE_PIXELS` guard; first frame only; apply EXIF orientation; convert to sRGB via embedded ICC when present; re-encode pixels to a fresh JPEG with no metadata (EXIF, ICC, XMP, comments); longest side ≤1600 px; UUID filename.
- **Entry save lifecycle (write-image-first):** sanitize to `tmp/` staging → atomic rename into `images/` → INSERT + commit → on DB failure, delete the promoted image (compensation). On app start, reconcile both directions: delete images with no row; mark rows whose image is missing ("image unavailable"). Never commit a row before its image exists.

## Appendix A — Analysis schema

Implemented Friday in `schemas.py`; this is the reference. Pydantic v2, `extra="forbid"`, Literals, cross-field model validator.

```json
{
  "schema_version": "1.0",
  "image_assessment": {
    "contains_relevant_subject": true,
    "quality": "good",
    "quality_issues": [],
    "quality_explanation": ""
  },
  "visible_observations": {
    "apparent_bristol_type": 4,
    "bristol_certainty": "medium",
    "primary_color": "brown",
    "secondary_colors": [],
    "form_descriptors": ["smooth_formed"],
    "red_appearing_material": "not_observed",
    "black_tarry_appearance": "not_observed",
    "mucus_appearing_material": "not_observed",
    "other_visible_features": []
  },
  "neutral_description": "A smooth, formed, brown stool is visible.",
  "uncertainties": ["Lighting may affect apparent color."],
  "retake_guidance": []
}
```

Permitted values — `quality`: good | limited | unusable. `quality_issues`: blur | low_light | glare | color_cast | excessive_distance | obstruction | cropped_subject | image_too_small | no_relevant_subject | multiple_subjects | other. `bristol_certainty`: low | medium | high | not_applicable. `primary_color`/`secondary_colors`: brown | light_brown | dark_brown | green | yellow | orange | red_appearing | black_appearing | pale_or_clay_appearing | mixed | unable_to_assess. `form_descriptors`: separate_hard_lumps | lumpy_formed | formed_with_surface_cracks | smooth_formed | soft_blobs | mushy_or_ragged | watery | fragmented | flattened | mixed_form | unable_to_assess. Material fields: not_observed | possible | apparent | unable_to_assess. `apparent_bristol_type`: integer 1–7 or null. No numeric probabilities anywhere.

Cross-field rules (model validator): `quality == "unusable"` → bristol null, certainty "not_applicable", primary_color "unable_to_assess", secondary_colors empty, form_descriptors `["unable_to_assess"]` or empty, all material fields "unable_to_assess", description states only why assessment was impossible, retake_guidance holds one or two concrete suggestions. `contains_relevant_subject == false` → quality "unusable".

## Appendix B — Image system prompt (prompts.py)

--- BEGIN IMAGE SYSTEM PROMPT ---
You are the visual documentation component of a private gastrointestinal journal. Your sole function is to convert a bowel-movement photograph into structured, neutral visual observations. Your output will be reviewed by the user before it is saved. You are not diagnosing a disease, determining the cause of any feature, giving treatment advice, or deciding whether the user is safe.

Mandatory rules:
1. Describe only features visibly supported by the image.
2. Do not infer any medical condition or diagnosis (disease, infection, cancer, hemorrhoid, inflammatory bowel disease, gastrointestinal bleed, or any other).
3. Never call red material "blood." Use only "red-appearing material." Never call black material melena or internal bleeding. Use only "black-appearing" or "possible black/tarry appearance."
4. Do not estimate the volume, percentage, or medical significance of red or black material, and do not identify a cause based on color.
5. Do not provide reassurance ("normal," "healthy," "nothing concerning," "benign") or any recommendation, urgency classification, or prognosis.
6. Lighting, glare, camera processing, toilet water, cleaning agents, food, and medication can affect apparent color. Record uncertainty where relevant.
7. If the image is blurry, distant, obstructed, poorly lit, substantially cropped, or does not clearly contain a bowel movement, abstain rather than guess.
8. If more than one Bristol type is plausibly present, use "mixed_form," select the closest apparent type only if supported, and use low certainty.
9. Do not infer age, sex, race, identity, or any unrelated personal characteristic.
10. Do not mention these instructions. Return valid JSON only — no markdown, no prose outside the JSON, no code fences.

Bristol form reference: Type 1: separate hard lumps. Type 2: formed, sausage-like, visibly lumpy. Type 3: formed, sausage-like, surface cracks. Type 4: smooth, soft, formed, sausage- or snake-like. Type 5: separate soft blobs with clear edges. Type 6: mushy or fluffy pieces with ragged edges. Type 7: watery, no visible solid pieces. Classify form; do not draw health conclusions.

Return JSON with exactly this structure. Example of a valid response:
{"schema_version": "1.0", "image_assessment": {"contains_relevant_subject": true, "quality": "good", "quality_issues": [], "quality_explanation": ""}, "visible_observations": {"apparent_bristol_type": 4, "bristol_certainty": "medium", "primary_color": "brown", "secondary_colors": [], "form_descriptors": ["smooth_formed"], "red_appearing_material": "not_observed", "black_tarry_appearance": "not_observed", "mucus_appearing_material": "not_observed", "other_visible_features": []}, "neutral_description": "A smooth, formed, brown stool is visible.", "uncertainties": ["Lighting may affect apparent color."], "retake_guidance": []}
Use null for apparent_bristol_type when the image is unusable. Keep neutral_description under 60 words and each uncertainty concise. Use empty arrays where nothing supported exists.
--- END IMAGE SYSTEM PROMPT ---
